# DIA SCAN implementation report

Implementation and verification completed locally on 2 October 2026, Asia/Jakarta. No production deployment was performed. Operational instructions and the complete route/schema reference are in [consultations.md](consultations.md).

1. **Audit findings.** Existing patients link to users; providers are users with a stored provider role. Examinations already link to assessments, protected foot images, persisted AI confidence/marked-area values, categorical risk results, and medical reviews. Latest pre-existing migration: 004. There is no provider assignment table. Existing provider review access covers the patient directory globally; communication access is restricted to named participants. Password/Google authentication uses the same existing JWT middleware and protected React routes. No authentication or model behavior was replaced.

2. **Architecture chosen.** Extend the existing Go handlers/repositories/models/routes and React API/pages/components/hooks. Persist clinical/communication metadata in PostgreSQL. Use one authenticated WebSocket for chat delivery, notifications, and native browser WebRTC audio signaling. Database-backed recipient events support backend replicas. No new frontend dependency or independent backend/authentication service.

5. **Database migration.** `005_monitoring_consultations.sql` is additive. It creates seven tables and their participant/history/unread/schedule/cursor/expiry indexes plus two defaulted review columns. It was applied successfully to an isolated PostgreSQL 18 database after 001–004. It was not applied to Neon. Apply it before deploying the extended backend; prior application versions remain compatible with the additive schema.

6. **New tables.** `conversations`, `messages`, `appointments`, `call_sessions`, `realtime_tickets`, `realtime_events`, `notifications`. Appointments/calls derive patient/provider/examination identity through their conversation. New review columns: `conclusion`, `followup_recommendation`. See the guide for all columns/indexes.

7. **New API endpoints.** `/api/progress`; `/api/provider/patients/:id/progress`; `/api/examinations/:id/comparison`; `/api/provider/review-queue`; `/api/consultation/providers`; conversation list/create/detail/messages/read/calls; appointment list/create/PATCH; call create/detail/PATCH/ice-config; notifications list/read; realtime ticket/upgrade. Methods and payloads are listed in the guide. Original routes/envelopes remain available.

8. **WebSocket implementation.** JWT-authenticated REST issues one-use 30-second tickets; hashes are stored. Browser authenticates in the first socket frame, keeping credentials out of URLs. Exact origin checking, expiry, active-account/role rechecks, size/rate/time limits, cursor replay, keepalive, and reconnect are implemented. Private database recipient events commit atomically with persisted messages. REST/polling remains authoritative and available when the socket disconnects.

9. **Chat authorization.** SQL ownership checks on list/detail/history/send/read and related appointments/calls. Patient IDs and sender identity are derived from JWT; provider role/activity and optional examination ownership are checked server-side. Unrelated providers, unrelated patients, and forged sender IDs are rejected. Messages render as text. Pagination: 50 messages per request; 3000-character maximum. Read acknowledgments include the highest displayed message ID.

10. **Appointment workflow.** Patient requests a future local-time consultation (converted to UTC) and may cancel. Provider confirms/cancels and completes a confirmed appointment after its start. Terminal states cannot reopen. Provider-row locking rejects overlapping 30-minute confirmed slots. Participants receive in-app notifications. Timestamps use TIMESTAMPTZ and local zone labels in the UI.

11. **WebRTC signaling architecture.** Create/authorize the call through JWT REST, then exchange caller offer, callee answer, and ICE over the same socket. The backend verifies participants/direction/active status, records call metadata, and emits state changes. Browser audio uses `getUserMedia({audio:true,video:false})`; no camera, recording, PSTN, or raw audio persistence. UI supports incoming/accept/reject, connecting, duration, mute, end, failures, cancellation cleanup, and acceptance in another tab.

12. **STUN/TURN status.** STUN default and authenticated ICE-config endpoint are implemented. Optional coturn REST credentials are generated by the backend and expire in 15 minutes. TURN infrastructure was not provisioned or tested. **TURN server required for reliable production calls.** Real cross-network connectivity has not been validated.

13. **Progress-monitoring logic.** Latest 100 actual examinations, each stored AI result shown separately, categorical risk/review timeline, unavailable-data states, and immediately previous examination comparison. Zero/one/multiple history cases are backend-tested. Neutral change wording only; no automated medical conclusion or invented numerical risk model. Desktop/mobile comparison layout checks passed.

14. **Provider-review changes.** Queue includes older completed examinations rather than only latest-per-patient records. Explicit ordering: unreviewed/pending by stored high/moderate/low risk, follow-up, approved; oldest first within groups. Existing notes/status behavior is retained with optional provider-authored conclusion/follow-up. Those fields appear in patient results and downloadable summaries. Review saves notify patients.
